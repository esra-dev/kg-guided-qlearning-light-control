# Documentation index

The result data themselves live under `results/` (see [../results/README.md](../results/README.md)).
This folder holds the documents that explain the system and the documents that define and
report the campaigns. A first-time reader starts with the [README](../README.md) at the
repository root, then [ARCHITECTURE.md](ARCHITECTURE.md) and [EXPERIMENTS.md](EXPERIMENTS.md).

## Guides

| Document | Contents |
|---|---|
| [ARCHITECTURE.md](ARCHITECTURE.md) | The parts of the system and how they talk to each other; the learning loop; how knowledge enters (starting values, soft preference, fade); the knowledge layers; fault detection and exclusion; delay learning and the deadline planner. |
| [LABS.md](LABS.md) | Every lab: zones, devices, light formula as coded in its flow, sun levels, targets, special features, port and files; which phase uses which lab. Generated by `scripts/make_labs_doc.py`; do not edit by hand. |
| [EXPERIMENTS.md](EXPERIMENTS.md) | Phases, arms and run modes, seeds and pairing, the workflows and their inputs, receipts, how a campaign is started, archived and pinned. |

| [VOCABULARY.md](VOCABULARY.md) | The vocabularies of the knowledge graphs (Brick, Elementary, SOSA/QUDT, Web of Things, the project's own terms), which Elementary terms are official, and a worked example. |

## Registrations, notices, reports and evidence

| Folder | Contents |
|---|---|
| `registrations/` | Registrations, protocols and dispatch records; each states when it was written relative to the data it governs, and the exploratory ones are marked as outcome-sighted. Start with `pre_registration.md`; each corrected or later campaign has its own registration and dispatch record. |
| `notices/` | One notice per phase explaining why the results of the first protocol were withdrawn and which corrected campaign replaces them. |
| `reports/` | Result reports that stand as they are. The reports of record for the other campaigns are the `CAMPAIGN_MANIFEST.md` and `ARCHIVE_MANIFEST.md` files inside each archive under `results/`. |
| `evidence/` | Small evidence tables and schemas cited by the reports, registrations and code (gate-manifest schema, Elementary term conformance, adaptation-settings evidence, post-hoc robustness tables, SPARQL execution capture, Phase-1b flow smoke), and `evidence/reproduction_check_2026-11/` (fresh GitHub runs compared with the archives, see its README). |

## Documents kept as written

The registrations, dispatch records, notices and reports are historical records. They are
not edited after they were committed (the three reports copied from the former state
report say so in their headers), because each states what was known, planned or decided at
its date. They therefore name scripts, documents, folders, labs, run modes and working
arrangements of their time, some of which no longer exist, and their line numbers and
function names refer to the code of their date. They name other documents by the paths
those had when they were written:

- `docs/<name>` for a registration, dispatch record or protocol now means
  `docs/registrations/<name>`; for a protocol-affected notice, `docs/notices/<name>`;
  for `phase1_results_v2.md` and `posthoc_robustness_2026-11-13.md`, `docs/reports/<name>`.
- `docs/audit/<name>` for an evidence table or schema now means `docs/evidence/<name>`.
- Archive folders such as `phase1_v2_corrected/` now sit under `results/`.

The same holds for the manifests inside the archives (`CAMPAIGN_MANIFEST.md`,
`ARCHIVE_MANIFEST.md` under `results/`): they are part of the archived bytes, are never
edited, and name the paths of their time (see [`results/README.md`](../results/README.md)).
